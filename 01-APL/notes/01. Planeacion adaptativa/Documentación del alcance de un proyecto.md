# Documentación del alcance de un proyecto

> PDF: [[documentation/01. Planeacion adaptativa/Documentación del alcance de un proyecto.pdf|Ver PDF original]]

Para **documentar el alcance** del proyecto, con sus requisitos y funcionalidades utilizarás la redacción de **épicas** e **Historias de Usuario** con el propósito de evitar una documentación extensa. Esta es la forma común de integrar el alcance en un proyecto ágil.

---

## Redacción de Historias de Usuario

La redacción de **Historias de Usuario** es una declaración de **¿quién quiere qué?** y **¿por qué?** De esta forma se facilita la transmisión de las **necesidades, requerimientos y expectativas** al equipo de desarrollo de una manera clara y comprensible para todos.

- Procura que la redacción de las Historias de usuario se realice con un **lenguaje sencillo** para facilitar que las personas puedan entender claramente el requerimiento y de esa manera puedan **definir las tareas adecuadas para cumplirlos**.
- Para cada HU, asegúrate que se incluyan los **criterios de aceptación** que servirán para verificar que los entregables se han realizado de manera adecuada — el *stakeholder* deberá manifestar cuál será la forma de validar que el **objetivo asociado ha sido cumplido**.

### Ejemplo: Historias de Usuario de Abril

| ¿Quién quiere qué? | Ejemplo |
|--------------------|---------|
| **El papá** — "Como un papá responsable, quiero que la casa cuente con un sistema de seguridad con comunicación directa a las autoridades más cercanas". | "Para vacacionar con confianza". |
| **La mamá y la tía** — "Como buenas cocineras, queremos una cocina amplia y bien equipada". | "Para preparar ricas comidas para la familia y amigos". |
| **Hermano menor** — "Como joven popular, quisiera que cuente con un buen sistema de sonido". | "Para disfrutar de las reuniones con mis amigos". |
| **Abril** — "Necesito un lugar donde pueda adaptar un karaoke y una piscina". | "Para tener momentos de diversión y convivencia con mi familia." |

> La HU de Abril debe separarse en dos historias de usuario para poder atenderlas adecuadamente.

## Stakeholders "dummy"

En este punto, es importante **escuchar y documentar las necesidades** de cada uno de los *stakeholders*. Incluso en algunos proyectos se adicionan *stakeholders* **"dummy"**, con la finalidad de complementar requisitos que los *stakeholders* reales no incluyen en este momento.

Cada *stakeholder* "dummy" se tipifica bajo el concepto **"Persona"** en una ficha con las siguientes características:

| Datos | Descripción |
|-------|-------------|
| **Nombre o alias:** | Para identificar rápidamente al personaje que representa. |
| **Datos demográficos:** | Para clasificar al personaje en un segmento de la sociedad. |
| **Descripción:** | Datos generales que ayuden a conocer mejor al personaje. |
| **Objetivos:** | Necesidades del usuario que los distingue de los demás. |

Identificar los datos anteriores te ayudará a tener documentadas las bases por las que se desarrollan HU basadas en estas "personas" y podrán ser consultados en caso de dudas del equipo de desarrollo.
